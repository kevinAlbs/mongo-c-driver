## Project Goal

This branch (`async-rust-poc`) is a prototype of an **async C driver** that wraps the Rust MongoDB driver via FFI. The objective is to expose a non-blocking async API to C callers using Rust's async/await and Tokio, bridged through a C-compatible `Future` type.

The design is documented in `../write-ups/Proposal1-Future/`.

## Build Commands

Prerequisites: `cargo`, `cbindgen`.

```bash
# Configure (enable Rust layer)
cmake -S . -B cmake-build -DENABLE_RUST=ON

# Build the Rust library and generate the C header
cmake --build cmake-build --target mongoc-rust-target --parallel

# Build all C tests (includes Rust integration tests)
cmake --build cmake-build --target test-libmongoc --parallel

# To run one CRUD test to spot-check the Sync C driver
./cmake-build/src/libmongoc/test-libmongoc --no-fork --match "/crud/unified/find"

# Run all CRUD tests with the Sync C driver
./cmake-build/src/libmongoc/test-libmongoc --no-fork --match "/crud/unified/*"

# Run only Rust-related C integration tests (requires a running mongod on localhost:27017)
./cmake-build/src/libmongoc/test-libmongoc --no-fork --match "/rust/*"

# Run Rust unit tests directly
cargo test --manifest-path src/rust/Cargo.toml

# Format C/C++ code
python tools/format.py --mode apply

# Check formatting without applying
python tools/format.py --mode check
```

## Architecture: Rust FFI Layer (`src/rust/`)

The Rust layer compiles to a static library (`libmongoc_rust.a`) and uses `cbindgen` to auto-generate `mongoc-rust-private.h`. This header is consumed by C code.

### Object Ownership and Lifetimes

The ownership hierarchy mirrors the MongoDB driver hierarchy and enforces Rust lifetime safety across the FFI boundary:

```
Client  (owns tokio::runtime::Runtime + mongodb::Client)
  └─ Database<'r>  (borrows runtime from Client)
       └─ Collection<'r>  (borrows runtime from Database)
            └─ Future<'r>  (borrows runtime from Collection or Database)
```

- Objects are heap-allocated via `Box::into_raw()` on creation and freed via `Box::from_raw()` in `_destroy` functions.
- The C caller owns all objects and is responsible for calling the matching `_destroy` function.
- `Database` and `Collection` must not outlive the `Client` that created them (enforced by Rust lifetime `'r`).

### Naming Conventions

C type names are generated by `cbindgen` from the `[export.rename]` section in `src/rust/cbindgen.toml`:
- `Client` → `mongoc_async_client_t`
- `Database` → `mongoc_async_database_t`
- `Collection` → `mongoc_async_collection_t`
- `Future` → `mongoc_async_future_t`
- `BsonView` → `bson_unowned_t` (non-owning view into a `bson_t` buffer)
- `BsonOwned` → `bson_owned_t` (heap-allocated BSON bytes returned from operations)
- `_set_comment_value` setters accept `const void *`; pass `bson_iter_value(&iter)` or `&(bson_value_t){...}` (libbson type)

Function naming follows two prefixes:
- **`mongoc_async__await<type>_<op>`** — blocks the calling thread until the operation completes; returns the result directly (e.g., `bool`, `bson_owned_t *`, cursor pointer).
- **`mongoc_async_<type>_<op>`** — returns a `mongoc_async_future_t *` immediately; the caller must drive the future to completion.

To prevent a type or item from appearing in the generated header, annotate it with `/// cbindgen:ignore`.

### Async Pattern: The Future API

Every async operation has two variants:
- **Synchronous**: blocks until completion (e.g., `mongoc_async_database_drop_await`)
- **Async**: returns a `*mut mongoc_async_future_t` immediately (e.g., `mongoc_async_database_drop`)

The C caller drives a future using this poll loop pattern:
```c
mongoc_async_future_t *future = mongoc_async_database_drop(db);
while (!mongoc_async_future_poll(future)) {
    mongoc_async_future_make_progress(future);
}
bool ok = mongoc_async_future_get_void(future);
mongoc_async_future_destroy(future);
```

Key future functions:
- `mongoc_async_future_poll()` — polls once using a noop waker; does **not** drive IO by itself
- `mongoc_async_future_make_progress()` — drives Tokio IO/timer drivers; must be called between polls
- `mongoc_async_future_poll_with_timeout(future, ms)` — blocks up to `ms` milliseconds
- `mongoc_async_future_get_void/int32/uint64(future, ...)` — extracts the result after poll returns `true`

### FutureValue Enum

`FutureValue` is a typed enum that wraps `FfiFuture<Result<T, Error>>`. Adding a new return type requires:
1. Adding a variant to `FutureValue` in `src/rust/src/future.rs`
2. Adding a matching arm to the `future_value_op!` macro
3. Adding a `mongoc_async_future_get_<type>()` extractor function

### BSON Interop

`BsonView` (`bson_unowned_t`) is a `#[repr(C)]` struct holding `data: *const c_void` and `len: usize`. It is a non-owning view into a `bson_t` buffer allocated by libbson. The Rust side deserializes it via `Document::from_reader`.

`BsonOwned` (`bson_owned_t`) is a heap-allocated BSON document returned by operations like `mongoc_async_collection_find_one_await`. Destroy with `bson_owned_destroy()`. Access as a view with `bson_owned_as_view()`.

### Tokio Runtime

Each `Client` creates a `current_thread` Tokio runtime. This runtime is passed by reference (`&'r tokio::runtime::Runtime`) to all child objects. Using `current_thread` means IO and timer drivers only run when `Runtime::block_on` is active on the calling thread — this is why `mongoc_async_future_make_progress()` is needed between polls.

### Logging

Rust code logs errors to the C logging system via `crate::log::error(MONGOC_LOG_DOMAIN, &msg)`, which calls `mongoc_log()`. Each module defines `const MONGOC_LOG_DOMAIN: &str` (e.g., `"client"`, `"database"`, `"collection"`).

## Test Infrastructure

C integration tests are in `src/libmongoc/tests/test-mongoc-rust.c` and registered via `test_mongoc_async_install()`.

- `TestSuite_Add` — unit tests (no MongoDB required)
- `TestSuite_AddLive` — integration tests (require `mongod` on `localhost:27017`)

Test names follow the path pattern `/rust/<type>/<operation>`, e.g., `/rust/collection/insert_one`.

The Unified Test Runner runs JSON specification tests. The Sync C Driver implementation of the Unified Test Runner is in `src/libmongoc/tests/unified`.

## Reference: Rust Driver Source

A local copy of the Rust MongoDB driver source is at `~/code/mongo-rust-driver/`. The `src/` directory contains the driver implementation. This is useful for looking up the async API surface being wrapped (e.g., `mongodb::Client`, `mongodb::Database`, `mongodb::Collection` methods).

## Reference: Specifications

A local copy of the MongoDB driver specifications is at `~/code/specifications`. This includes markdown files describing driver specifications and API expectations. This includes tests written in JSON (generated from YAML) that drivers use to verify conformity. The C driver includes copies (some outdated).
